01 / Overview

A runtime pattern drawn from a working integration.

avolzila_runtime names the generalized host approach developed from the VP64 implementation. Its job is to bridge a native program and the environment that presents it: machine execution, input, picture and sound, then a device-specific frontend.

VP64 is the concrete reference case behind this page. The Raspberry Pi image, avolzila_platform, provides an embedded host environment; Apple versions package the experience as products for end users. The runtime sits between the program and those hosts.

03 / Under the hood

Inside the VP64 reference implementation.

The current VP64 code demonstrates the runtime pattern in concrete terms: embed the game, advance the PAL machine one frame at a time, then hand picture, sound and controls to a host frontend.

No stock KERNAL or BASIC ROMs.

The VP64 implementation provides its own small compatibility KERNAL and a blank BASIC image. The original Commodore 901225-01 character ROM is embedded for the game’s glyphs, alongside the VP64U cartridge. Everything needed is packaged into the executable, so no external ROM files are required when it runs.

01

Cartridge at startup

The raw 64 KiB Magic Desk image is embedded at build time. During execution, a write to $DE00 selects one of eight 8 KiB banks at $8000–$9FFF. A small compatibility KERNAL provides the startup, keyboard, and interrupt entry points the game uses.

02

PAL timing

The C11 chips model supplies the C64 components; a C++23 Machine wrapper drives them. Each frame advances 63 × 312 CPU ticks, approximately 50.1 PAL frames per second.

03

Host-facing output

The wrapper converts the indexed C64 display to RGBA pixels and passes 44.1 kHz mono SID samples to an audio callback. SDL places the 320 × 200 game picture inside the cabinet and maps keyboard, pointer, and touch input to game controls.

04

Cabinet feedback

VP64 writes its game state to $DE01–$DE09. The final write commits a complete snapshot, which the frontend uses for button lamps and selected holds. The core makes one checked allocation at construction and no heap allocations while advancing or resetting the machine.
